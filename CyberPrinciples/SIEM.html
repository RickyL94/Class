WHAT IS SIEM?
DEFINITION

Security Information and Event Management

Security Information Management: Collecting, retaining, searching, and reporting on security-relevant data.

Security Event Management: Monitoring events, identifying patterns, and generating alerts for investigation.

SIEM: A platform and set of practices for bringing security data together to support search, detection, investigation, and reporting. It does not automatically identify every attack.

DATA TRANSFORMATION
PARSING & NORMALISATION

Consistent fields make searches reusable

Parsing extracts useful values from an event, such as an account, source address, process name, or event identifier.

Normalisation maps source-specific fields to consistent names where a schema or data model is configured. Different sources may call the same concept by different names.

In Splunk, the Common Information Model (CIM) is a framework for consistent field naming and data models across supported data. It requires suitable configuration and field mappings.

DETECTION APPROACHES
RULES & SIGNALS

Detections produce leads—not final verdicts

Threshold

Flag a count or rate above a defined baseline, such as repeated failed logins.

Behavioural signal

Identify activity unusual for an account or asset, then check context and data quality.

Sequence

Relate multiple event types in a defined order or time range.

Prioritisation should account for confidence, impact, asset importance, and known limitations. Tune with evidence and document changes.

EXAMPLE DETECTION
WINDOWS EVENT 1102

Audit log cleared: investigate the context

Event ID 1102 can indicate that the Windows Security audit log was cleared. Treat it as a high-priority signal, not proof of compromise.

  • Confirm the event source, host, timestamp, and actor.
  • Check for authorised maintenance or administrative activity.
  • Review neighbouring logons, process events, and changes.
  • Preserve relevant evidence and follow escalation procedures.
MEET SPLUNK
A COMMON DEPLOYMENT VIEW

Forwarders, indexers, and search heads

Forwarder

Collects selected data and sends it onward. Agent choice depends on the source and operational requirements.

Indexer

Processes incoming data, creates indexed structures, and stores them for searching.

Search head

Provides the search interface and coordinates searches, dashboards, and alerts in a distributed deployment.

Architecture, responsibilities, and scale vary. A small standalone deployment differs from a clustered production environment.

OPERATING-SYSTEM TELEMETRY
LINUX & WINDOWS EXAMPLES

Know where useful evidence may appear

Linux

Authentication may appear in /var/log/auth.log or /var/log/secure, depending on distribution and configuration. System and service logs may use files or journald.

Windows Security

4624: successful logon; 4625: failed logon; 1102: audit log cleared. Availability and detail depend on audit policy.

Process / PowerShell

4688: process creation when configured; Sysmon Event 1: process creation when Sysmon is installed; PowerShell 4104: script-block logging when enabled.

INGESTION OPTIONS
CHOOSE FOR THE SOURCE

Common paths into Splunk

  • Universal Forwarder: A common option for selected endpoint and server data.
  • Syslog: Network devices often send events to a dedicated collector, which can forward them to Splunk. Transport and security controls matter.
  • HTTP Event Collector: Token-based HTTP interface for application and service events; protect tokens and endpoints.
  • File input: Useful for controlled testing or analysis; not a substitute for a managed production pipeline.

Validate source coverage, timestamps, parsing, access controls, retention, and operational ownership.

DECISION & RESPONSE
AFTER INITIAL TRIAGE

Separate the assessment from the action

Potential true positive

Preserve evidence, escalate promptly, and coordinate response through the authorised incident process.

Potential false positive

Record the benign explanation and evidence. Tune rules carefully, test changes, and monitor their effect.

Unclear

Keep the case open or seek further evidence; do not force certainty when evidence is incomplete.

Isolation, credential changes, and other containment actions require appropriate authority and coordination.

PROCESS ALERT
EVIDENCE & CONTEXT

What a process alert can—and cannot—tell us

Process event

Windows Event 4688 may record a process start when the relevant audit policy is enabled. Useful fields can include host, account, process path, command line, and parent process.

Related activity

Nearby logon, file, and network records can add context. The quality of any link depends on timestamps, identity mapping, and available telemetry.

Assessment

An encoded command may warrant attention, but it is not by itself proof of malicious activity. Legitimate administration and software can also use scripts.

Interpretation is evidence-led: note what is observed, what is inferred, and what remains unknown.

LIMITATIONS
WHAT CAN GO WRONG?

A SIEM is only as useful as its evidence and operation

Coverage gaps

Missing sources, disabled audit policies, dropped events, or short retention.

Data quality

Clock skew, inconsistent identities, poor parsing, or incorrect field mappings.

Operational constraints

Alert fatigue, cost, access control, ownership, and changing infrastructure.

Detection engineering includes validating data sources and monitoring pipeline health—not only writing rules.

TAKEAWAYS
WRAP-UP

Evidence first. Context always.

1. Centralise thoughtfully: choose telemetry that supports defined investigation and detection needs.

2. Validate the data: parsing and consistent fields help, but configuration and coverage determine what is searchable.

3. Treat alerts as leads: correlate, investigate, document uncertainty, and use authorised response procedures.
