FEDERATED LEARNING / SECURITY & PRIVACY
01 / The problem

Security teams can learn from each other, but they cannot always share private data.

Traditional approach

Centralise the data

Collect logs, transactions, endpoint telemetry or user records in one place, then train a model centrally.

Risk: a high-value data lake, larger breach impact, access-control complexity and regulatory exposure.

Federated approach

Move the learning to the data

Each organisation or device trains locally. It sends model updates rather than its raw training records.

Potential benefit: less raw-data movement and more opportunities for cross-silo collaboration.

Federated learning can reduce data sharing, but it does not automatically keep information secret or meet every privacy law.
THE DATA-SHARING DILEMMA
02 / Centralised vs federated

Two ways to build one shared model

Centralised

Data travels to the model

Logs, transactions, endpoint telemetry and user records are collected in one place, then a model is trained centrally.

One high-value target: a single breach exposes everything, with maximum regulatory and access-control exposure.

Federated

The model travels to the data

Each organisation trains locally on its own data and sends only model updates to the coordinator.

Boundary stays closed: raw data never crosses organisational lines, so collaboration becomes possible across silos.

Core trade-off: centralisation buys simplicity and one clear owner; federation buys data locality and cross-organisational collaboration — but the model updates themselves are new artefacts that must be protected.

THE FEDERATED TRAINING LOOP
04 / Centralised vs federated

Same goal, different risk profile

Data movement

Centralised: bulk transfer of raw logs and records into one lake.
Federated: only compact model updates cross the boundary.

Breach impact

Centralised: one lake is one large target — maximum blast radius.
Federated: each organisation's data stays local; the coordinator holds aggregates, not source records.

Regulatory exposure

Centralised: cross-border or cross-silo transfers trigger data-protection review.
Federated: data residency is easier to preserve when records do not leave.

Trust model

Centralised: everyone trusts the central owner and its controls.
Federated: participants must trust the coordinator plus the aggregation and privacy controls.

Coverage

Centralised: as good as the data that managed to arrive.
Federated: the model learns from populations no single organisation can see alone.

Operations

Centralised: storage and bandwidth for large one-off transfers.
Federated: repeated rounds of smaller updates, and a coordinator that must itself be protected.

Neither is universally better — the right design depends on data sensitivity, the law, and who can be trusted to hold what.
SIDE BY SIDE
05 / Security use cases

Where federated learning can help cybersecurity

Threat detection

Collaborative anomaly detection

Organisations train on local network or endpoint telemetry to improve detection of suspicious behaviour without exchanging raw logs.

Fraud prevention

Cross-institution fraud models

Banks or payment providers learn from different customer populations while limiting direct sharing of transaction histories.

Edge / IoT

On-device threat intelligence

Devices learn patterns of malicious activity locally and contribute updates when connectivity and policy permit.

Identity & access

Privacy-aware behaviour analytics

Participating services can improve risk scoring without building a single repository of all user activity.

APPLICATIONS
06 / Case study

Case study: collaborative phishing detection across three enterprises.

Three organisations want a shared classifier for suspicious messages while retaining email content and user identities within their own environments.

Local preparation

Each enterprise extracts approved, minimised features and labels within its own security boundary.

Federated rounds

An authenticated coordinator distributes a signed model; clients train locally and submit protected updates.

Safeguards

Protected combining of updates, client-level privacy where justified, clipping, robust validation and strict model access.

Operational use

A validated model is deployed in monitor-only mode, then gradually integrated into response workflows.

Do not send raw email content or personal identifiers into the training federation unless explicitly justified, authorised and protected.
FEDERATED LEARNING / CYBERSECURITY & PRIVACY
07 / Privacy reality check

Even when raw data stays private, shared updates can reveal information.

Gradient / model inversion

An attacker tries to work backwards from the updates to guess private information.

Checking who was in the training data

An attacker tries to find out whether a person's information was used to train the model.

Guessing facts about a group

Updates reveal sensitive characteristics of a participant's dataset, even without recovering exact records.

Exposure of activity details

Participation patterns, timing, device identifiers and update sizes can disclose operational information.

Privacy threat model: protect not only the dataset, but also updates, identities, metadata, the trained model and the aggregation process.
FEDERATED ≠ AUTOMATICALLY PRIVATE
08 / Attacks

The new attack surface

Federated learning adds participants and a coordinator — each is a potential attacker or breach point.

Teaching the model incorrect information

A participant changes its training data to teach the model incorrect information.

Sending harmful model updates

A dishonest participant sends changes designed to make the model behave in the wrong way.

Pretending to be many users

An attacker pretends to be many different users so their changes have more influence.

The training organiser is hacked

A malicious or compromised server distributes manipulated models or targets selected clients.

Integrity threat model: a federation must assume that some participants are wrong, compromised or malicious — and design aggregation accordingly.
THREAT LANDSCAPE
09 / Defences

Layer controls around every round

Confidentiality

Protected combining of updates

Cryptographic protocols let the coordinator learn the combined result without seeing any single organisation's contribution.

Formal privacy

Differential privacy

Updates are clipped and calibrated noise is added, bounding how much the released model can reveal about one person.

Integrity

Robust aggregation

Medians, trimmed means and anomaly scoring limit the effect of poisoned or extreme updates.

Lifecycle

Participant controls

Identity and version checks, validation before acceptance, and the ability to suspend or exclude a client.

Two different jobs: privacy controls (protected combining, DP) and integrity controls (robust aggregation, vetting) are not substitutes — a real deployment needs both.
DEFEND IN DEPTH
10 / Decision

When does federated make sense?

Choose federated

Many organisations, similar data

Competitors, banks, hospitals or enterprises that must keep data local but want a shared detection model — e.g. phishing, fraud or endpoint threats.

Fits when: strict residency or privacy rules apply, and no single organisation holds the full picture.

Stay centralised

One owner, one trusted dataset

A small group of trusted partners that can lawfully share, or a single authoritative data lake inside one organisation.

Prefer central when: the federation would be tiny, trust is high, and a governed central pipeline is simpler to audit.

Design choice, not default: federated adds coordination complexity. It earns its cost when the data cannot move and the collaboration is worth having.
FIT CHECK
11 / Takeaways

Federated learning is one way to organise AI training. It is not a guarantee of privacy.

01

Keep data close to its source

Reduce central collection and enable collaboration across organisational boundaries.

02

Protect what leaves the client

Changes to the AI model, metadata and the global model all require threat analysis.

03

Combine privacy with integrity

Protected combining of updates and differential privacy must coexist with poisoning detection and governance.

04

Measure the trade-offs

Privacy, accuracy, communication cost, robustness and operational complexity must be evaluated together.

The goal is to build a useful shared model while keeping private information and systems safe.

Name that attack

Think back to the poisoned-update figure.

Quick check — ask the class first

A participant quietly sends updates that nudge the model to miss one specific phishing pattern. Which attack is this?

Why: This is model poisoning: the participant looks legitimate on the network, but the learning it contributes is corrupted. Exfiltration steals data out; man-in-the-middle intercepts traffic in transit; differential privacy is a defence (calibrated noise), not an attack. Secure channels alone can't catch poisoning — only robust aggregation, clipping and validation can.

Name that defence

Think back to the controls layered around every round.

Quick check — ask the class first

Which defence adds calibrated noise to updates before they are aggregated?

Why: Differential privacy: each update is clipped, then calibrated noise is added so no single record can change the released model by more than a bounded amount. Secure aggregation hides individual contributions with cryptography (confidentiality); robust aggregation resists extremes and poison (integrity); firewalls block traffic. Different jobs — real deployments need all of them.
